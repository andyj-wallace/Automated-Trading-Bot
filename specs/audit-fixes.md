# Spec: audit-fixes

## Goal
Fix five problems found in the strategy-to-trade audit so that strategies that use a market filter actually trade, strategy SELL signals close the positions they opened, valid signals are not rejected over sub-penny rounding, "Sell everything" also stops in-flight buys, and a raised trailing stop survives a restart. For the single operator of this paper-trading bot.

## User stories / requirements
- As the operator, I want enabling a strategy to load the price history it needs, so that a strategy never silently holds forever for lack of data.
- As the operator, I want a strategy's SELL signal to close the position that strategy opened, so that exit rules like moving_average's death cross work.
- As the operator, I want "Sell everything" to leave no buy order working at IBKR, so that nothing opens after I flatten.
- As the operator, I want the trailing stop to survive a backend restart, so that a winning trade's protection is not lost.

- R1 (history backfill): After `create_strategy` or `patch_strategy` in `backend/app/api/v1/strategies.py` commits, and only when the engine is started (same guard as `add_symbol` in `backend/app/api/v1/symbols.py`), spawn `engine.bar_refresh.refresh(symbols, "2 Y")` through `engine.spawn(...)`, where `symbols` is the strategy's `config["symbols"]` plus the built strategy's `required_extra_symbols()`, all upper-cased. A failure to build the strategy for extra symbols is logged and the request still succeeds.
- R2 (scheduler sees new bars): After a backfill for a symbol completes, `StrategyScheduler` must use the new bars on its next cycle the same day (today `_bar_cache` in `backend/app/core/strategy_engine/scheduler_data.py` keeps a day's bars until the next day). The planner chooses the mechanism, which must not add broker calls to the scheduler.
- R3 (short-history warning): `BaseStrategy` gains `min_history_bars(self) -> int` returning 0 by default. Every built-in daily strategy returns the number of completed daily bars its rules need, including its regime period where it has one; `CompositeStrategy` returns the max of its sub-strategies. Before `generate_signal`, the scheduler calls `_warn_once("short_history", symbol, trading_day, ...)` when the symbol's bars, or any fetched extra symbol's bars, number fewer than `min_history_bars()`. It still calls `generate_signal` (behavior unchanged otherwise).
- R4 (SELL exits): Add `ExitReason.SIGNAL_EXIT = "SIGNAL_EXIT"` in `backend/app/db/models/trade.py`, the hand-written migration `backend/alembic/versions/0011_signal_exit.py` (`revision = "0011"`, `down_revision = "0010"`, `ALTER TYPE exitreason ADD VALUE IF NOT EXISTS 'SIGNAL_EXIT'` run the same way as 0010, and a `downgrade()` that runs without error and leaves the value, as 0010 does), and `"SIGNAL_EXIT"` in the `ExitReason` type in `frontend/src/types/api.ts`.
- R5 (SELL handling in the scheduler): in `SchedulerSubmitMixin` (`backend/app/core/strategy_engine/scheduler_submit.py`):
  - SELL and the symbol has no active trade: treated exactly like HOLD (no claim row, no `ZERO_QUANTITY` outcome, no order).
  - SELL and the symbol's active trade is OPEN with `strategy_id` equal to this strategy's id: skip every entry-only gate (the spread check, the liquidity check, sizing and risk validation), keep the ownership, OPEN-status and dedupe claim (`_claim_signal` with action `SELL`), then call `order_manager.close_position(trade.id, "SIGNAL_EXIT")` once and record outcome `f"EXIT_{outcome.value}"` (for example `EXIT_CLOSED`, `EXIT_MARKET_CLOSED`). An exception from `close_position` records outcome `EXIT_FAILED` with the error as detail.
  - SELL and the active trade belongs to another strategy, has no strategy (manual), or is not OPEN: ignored as today (logged, no claim, no close).
  - BUY handling is unchanged.
- R6 (composite "any" mode): in `CompositeStrategy.generate_signal` "any" mode, when `market_data.open_position` is False the first BUY wins and SELLs are skipped; when it is True the first SELL wins and BUYs are skipped. "all" and "majority" modes are unchanged.
- R7 (target rounding): every built-in strategy that rounds a take-profit to cents uses `ROUND_CEILING` for the take-profit only: `moving_average.py`, `mean_reversion.py`, `stock_trend.py`, `bull_bear.py`, `trend_pullback.py`, `intra_week_reversion.py` and `DayTradeStrategy.buy` in `intraday_common.py`. Stop-loss rounding is unchanged.
- R8 (flatten): flatten must leave no strategy buy able to open a position afterwards.
  - `OrderManager` gains an optional `is_paused: Callable[[], Awaitable[bool]] | None = None` constructor parameter (wired to `trading_state.is_paused` in `backend/app/core/engine.py`). Inside `_submission_lock`, before validation, `submit_order` rejects a request with a non-null `strategy_id` while paused, raising `RiskRejectionError` with reason prefix `TRADING_PAUSED` (no trade row, no audit entry). Manual entries (`strategy_id` None) are unaffected. For strategy entries, `submit_order` checks `is_paused` once more immediately before the broker call (after the SUBMITTED transition); if paused it sends nothing, moves the trade to CANCELLED, and raises `RiskRejectionError` with reason prefix `TRADING_PAUSED`.
  - `OrderManager` counts in-flight `submit_order` calls (from entering the lock until it returns or raises, including on errors) and exposes `async def wait_for_entries_idle(timeout: float) -> bool`, which returns True once none are in flight, or False at the timeout.
  - `flatten` in `backend/app/api/v1/trading.py`, after pausing, awaits `wait_for_entries_idle(30)` (a `False` adds one result `{"outcome": "ENTRIES_STILL_IN_FLIGHT"}` and flatten continues). Then, for each PENDING or SUBMITTED trade, it looks up `broker.find_order_by_ref(f"{trade.id}:entry")`:
    - WORKING: call `broker.cancel_order(...)`. `False` or an exception gives `ENTRY_CANCEL_FAILED`. On `True`, poll `find_order_by_ref` (every 0.25 s, up to 10 s, injectable for tests) until the order is no longer WORKING; still WORKING at the deadline gives `ENTRY_CANCEL_FAILED`. Otherwise continue with the settled state below.
    - Settled with `filled_quantity > 0` (FILLED, PARTIAL, or filled during the cancel): adopt the fill with `order_manager.adopt_entry_fill(trade.id, fill)`, using `broker.get_execution_summary(f"{trade.id}:entry")` when it returns a fill, else the order result (the same rule the reconciler uses), and record `ENTRY_ADOPTED`. The trade is now OPEN and is closed by the final sweep.
    - Settled with no fill, or no broker order: record `ENTRY_CANCELLED`; the trade row is left for the reconciler as today.
    - Any lookup error gives `ENTRY_CANCEL_FAILED` for that trade only.
  - Finally flatten reads OPEN trades (including those adopted above) and closes them exactly as today. Broker logic stays behind `BaseBroker`; the route stays thin (the flatten steps live in `app/core`).
- R9 (trailing stop persistence): `PositionMonitor` (`backend/app/core/execution/position_monitor.py`) persists the in-memory trailed stop to `trades.current_stop_price` when it has risen at least 0.1R above the last persisted value (R = entry_price minus the original stop). The write runs as a referenced task via `spawn()`, never blocks `on_price_update`, never lowers a stored value (enforced in the SQL update), and never writes `stop_loss_price`. Every other writer of `current_stop_price`, including `TradeRepo.set_stop_order`, must keep the larger of the stored and new values (`GREATEST`, treating NULL as absent), so placing or recovering a protective stop never overwrites a higher persisted trailing stop. A new `TradeRepo` method does the write. `_track` starts the live stop at the larger of `stop_loss_price` and `current_stop_price`, and the R unit still uses `stop_loss_price`. The IBKR stop order is not changed.
- R10 (docs): README "How a trade happens" lists the signal exit and states that enabling or changing a strategy downloads 2 years of history for its symbols and extra symbols; ROADMAP's "Persist the trailing stop" item is deleted; README says flatten is best effort (see Out of scope), signal exits do not run while trading is paused, and that backtests do not simulate signal exits.

## Constraints
- No new dependencies. Follow `.claude/CLAUDE.md` guardrails: money stays `Decimal`, no `float`; quantities stay `int`; no short selling; no take-profit orders sent to the broker; audit-immutable trade columns (`entry_price`, `stop_loss_price`, `take_profit_price`, `reward_to_risk_ratio`, `risk_amount`, `account_balance_at_entry`) are never written after creation; no exit is blocked, delayed or resized by growth mode, fees, settlement or day-trade rules.
- Every background task uses `spawn()` / `PeriodicTask` from `app/core/tasks.py`; no bare `asyncio.create_task`.
- Existing migration files under `backend/alembic/versions/` are not edited. The operator explicitly approved adding exactly one new file there, `0011_signal_exit.py` (`.claude/CLAUDE.md` names 0011 as the next free migration number); this is the only exception to the AGENTS.md "Do not touch" entry. `.env.example`, `frontend/package-lock.json`, `.github/workflows/ci.yml` and `docs/*.png` are not touched.
- New constructor parameters default to "off" so existing callers and tests keep today's behavior. Existing tests may be extended but not weakened.
- Log `extra={...}` keys never use reserved `LogRecord` attribute names.

## Out of scope
- Flatten is best effort, an accepted operator decision: it does not cover (a) an entry whose broker state is PARTIAL while still working, which flatten adopts and closes without cancelling the unfilled remainder (IBKR's `place_order` already cancels unfilled market-order remainders after its fill timeout), and (b) a strategy entry already inside the broker call when the 30-second idle wait times out. No new `BaseBroker` method for terminal order state is added.
- Moving the IBKR protective stop order as the trailing stop rises.
- Simulating SIGNAL_EXIT in the backtesting engine.
- Running signal exits while trading is paused (stops, targets and manual closes keep working as today).
- Changing the one-claim-per-strategy-symbol-day rule for BUY signals.
- Re-trying a backfill automatically if it fails (the existing `refresh` failure alert stays the signal).
